# Rust API 与资源生命周期约定

本文用于审查模块接口、原生资源所有权和失败路径。规则以当前实现为依据；新增或修改 API 时，应明确哪些状态由类型保证，哪些前提仍由调用方负责。目录归属见[目录结构](structure.md)，构建环境见[构建与验证](build.md)。

## 模块与接口边界

| 边界 | 当前职责 | 审查重点 |
| --- | --- | --- |
| `desktop-core` | 身份、几何、外观、项目、面板与工作区 | 模型约束不依赖 HWND 或窗口消息 |
| `desktop-storage` | 配置、数据库、事务与备份 | 输入校验、提交范围、恢复失败及错误传播 |
| `desktop-shell` | Shell 操作和 OLE apartment 守卫 | 线程要求、取消语义、COM 与原生对象所有权 |
| `app/src/pane` | UI 状态、窗口与后台结果协调 | 重入、窗口销毁、异步结果是否仍适用 |
| `native_graphics.rs`、`desktop-graphics` | 绑定互操作与图形资源 | 引用计数、设备身份、释放顺序 |

模块入口负责声明与重导出，具体实现放在所属模块。身份、模型校验和持久化规则应通过所属模块复用，避免在多个 UI 入口各自实现。

`Panel` 用私有 `PanelSource` 表示桌面、文件夹和搜索三种互斥来源。`Panel::new` 与 `set_rect` 都经过尺寸约束；来源切换由方法维护相关状态。新增接口应延续这些约束，不以多个可随意组合的公开字段表达互斥状态。锁定、置顶等独立偏好仍可分别保存，不必合并成互斥枚举。

## 所有权与线程归属

审查原生值时，先确定它是拥有的资源、借用的句柄，还是可跨线程传递的数据。复制一个指针或句柄数值不会延长底层资源的生命期。

| 对象 | 当前实现与约束 |
| --- | --- |
| `ShellApartment` | 由 `initialize_sta` 创建，不可直接构造、克隆、Send 或 Sync；每次成功初始化对应一次 `OleUninitialize` |
| COM 接口 | 使用所属绑定的拥有型接口管理引用；跨绑定转换通过 QueryInterface 取得独立引用 |
| HWND 与回调数据 | 核对窗口何时销毁、回调数据何时释放，以及失败分支是否撤销注册或归还所有权 |
| 应用图标 | `app_icon::Icon` 释放其拥有的 HICON；窗口使用的缓存图标须存活至窗口退出 |
| 后台结果 | 传递项目快照、像素等可共享数据；Shell 工作者在自己的线程初始化 apartment |
| 唤醒目标 | `Wake` 同步通知与解绑，防止销毁后仍向旧 HWND 投递工作通知 |

`Arc` 只提供共享所有权，不能替代对象本身的线程安全约束。后台工作者需要的 COM 对象留在所属线程；不要仅为通过编译给原生包装类型添加 `unsafe impl Send/Sync`。

## 正常退出与异常终止

主 UI 入口 `app/src/pane/hybrid.rs::run` 当前使用内部 `OleApartment` 守卫；Shell 工作者和相关测试使用 `desktop_shell::ShellApartment`。两者都要求依赖 OLE 的资源先释放，但它们不是同一个类型。

主 UI 作用域按“OLE 守卫 → `GraphicsLifetime` → 应用状态及窗口”的顺序声明，退出时按相反顺序释放。图形缓存通过显式清理入口释放，不留到进程退出时的线程局部析构。清理时先从 `RefCell` 取出对象、结束借用，再执行可能重入的原生释放操作。细节见[绘图与绑定](rendering.md)。

审查退出路径时需要分别确认：

- 正常关闭时，窗口、拖放注册、回调、定时器和工作通知的生命周期是否结束。
- 初始化中途失败时，已创建的资源是否由守卫或对应失败分支释放。
- 显式结束操作是否返回必要错误；`Drop` 仅承担不能遗漏的兜底清理，不应成为唯一的错误报告入口。
- 强制结束进程时，不依赖 Rust 析构执行。Explorer 内的桌面组件属于另一个进程，需由其会话恢复机制处理；见[架构说明](architecture.md#退出与异常终止)。

正常退出测试不能证明崩溃或强制终止后的恢复行为，主进程资源释放也不能直接证明 Explorer 内的 DLL 已卸载。

## 重入与后台通知

Shell 调用、菜单循环和同步窗口消息可能重入应用。不要在持有应用状态或模型的可变借用时调用可能回调到同一状态的原生入口。

常用顺序是：在短借用范围内读取参数或克隆所需句柄包装，结束借用，再执行原生调用；返回后重新借用并核对目标是否仍存在。需要延迟执行的操作使用现有消息机制，不能把借用跨越消息循环保存。

后台结果返回时，还应核对请求对应的来源、会话或窗口是否仍有效。唤醒只表示有状态需要检查，不应假定“一条通知恰好对应一个结果”；当前 `Wake` 会合并通知。调度规则见[后台调度](event-driven-runtime.md)。

## 错误、取消与提交边界

API 应区分“操作失败”“用户取消”和“成功但无变化”，沿用所属模块现有的返回类型。原生错误在需要诊断时保留 HRESULT 或底层错误信息，到 UI 边界再转换为显示内容；不要把所有失败折叠成 `false`。

持久化审查不能只检查是否调用了数据库事务：

- `WorkspaceStore::save_workspace` 在事务内保存工作区；关联配置文件另行写入，数据库提交失败时尝试恢复之前的配置内容。恢复也可能失败，不能据此承诺跨文件和数据库的原子提交。
- 内存模型修改是否恢复，由调用方负责；数据库回滚不会自动恢复 UI 模型或已经创建、销毁的 HWND。
- Shell 文件重命名成功后，后续保存或过滤同步失败不能当作文件系统操作从未发生。应协调已提交的新身份，具体路径见[图标菜单与重命名](pane-item-rename.md)。

新增多步骤操作应写清提交点、失败后保留的状态，以及是否需要刷新或重试。避免无条件重试已经产生外部副作用的步骤。

## Windows 绑定与 unsafe 边界

不同版本的 Windows Rust 绑定即使使用相同 ABI，也不是相同 Rust 类型。图形接口转换集中在 `app/src/pane/native_graphics.rs`；`native_interface` 通过 QueryInterface 获取独立引用，`create_layer` 借用调用方接口。不能把借用指针当成所有权转移，转换后的错误通过 `canvas_result` 回到应用侧类型。

每处 `unsafe` 应能回答以下问题：

- 指针指向的对象是否存活，缓冲区长度、布局和可写性是否匹配？
- 当前线程是否满足窗口或 COM apartment 要求？
- API 是借用还是接管资源，成功和失败分别由谁释放？
- 注册后的回调是否可能晚于状态销毁，注销和销毁是否会同步重入？
- 回调中的错误如何返回或报告，是否存在 panic 越过原生 ABI 边界的路径？

公有 unsafe 接口应记录调用方必须满足的安全前提，调用点说明这些前提如何成立。生成绑定由 `tools/windows-bindings` 维护，必要的 ABI 命名豁免留在生成边界；不手工修改生成文件。版本与生成检查见[绘图与绑定](rendering.md)。

## 修改后的验证

按改动选择测试，不把整套原生窗口测试作为每次接口调整的默认要求。以下入口覆盖模型约束、apartment 类型约束与图形退出顺序：

```powershell
# 领域模型及来源、几何和身份约束
cargo test -p desktop-core --lib --locked --offline

# ShellApartment 的不可跨线程、不可直接构造约束
cargo test -p desktop-shell --doc --locked --offline

# 每次成功 OLE 初始化均有对应释放
cargo test -p desktop-shell --lib nested_guards_balance_each_successful_initialization --locked --offline

# 图形资源先于 apartment 和进程退出释放
cargo test -p luciddesk --bin luciddesk graphics_caches_release_before_apartment_and_process_exit --locked --offline -- --test-threads=1
```

涉及存储、Shell 操作或窗口的改动，还需针对成功、取消、中途失败、目标销毁和重复调用检查状态与资源。会激活原生窗口的测试按说明独立运行；强制终止后的恢复单独验证。检查要求见[验证与兼容边界](validation.md)，在提交或问题报告中注明执行命令、环境、未覆盖路径及实机观察结果。
